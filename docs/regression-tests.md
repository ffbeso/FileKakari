# 回帰テスト

Windows、.NET 10 SDK、PowerShell 7以降で実行します。

```powershell
pwsh -NoProfile -File ./run_regression_test.ps1
```

本体を参照する専用コンソールをビルドし、実際のサービスを検証します。
UTF-8／CP932／ASCII／Markdownのテキスト内容、サイズ制限、ファイル消失、キャンセル、
PNGのデコード、フォルダ優先の昇降順列挙とメタデータ、セッションの往復保存、不正JSONが対象です。
新しいテストは `FileKakari.RegressionTests/Program.cs` の `CheckAsync` 呼び出しとして追加します。

プレビューでは、一覧領域を残すペイン縮小、縦長・横長画像のサイズ計算、原寸と総画素数の上限、
画像キャンセル、縦長PNGの実デコード、200% DPIでの解像度更新、メモリキャッシュ再利用、
表示枠拡大時の再デコード、更新日時変更・削除後のキャッシュ無効化を検証します。

プレビュー変更後の実操作確認:

* 右配置と下配置の両方でプレビューを大きくし、ウィンドウを縮める。一覧領域が確保され、プレビュー側が縮む。
* 縦長・横長・小画像を選び、ヘッダーや余白を除いた枠内に縦横比を保って表示される。小画像は原寸以上にならない。
* 境界のドラッグ、プレビュー最大化と復元、右／下配置の切り替えを行う。画像を保持して伸縮し、必要な場合だけ高解像度に更新される。
* 100%／150%／200%のモニター間を移動し、画像の大きさと鮮明さ、Shellプレビューの端の欠けを確認する。
* 画像を連続選択し、最後に選んだ画像が表示される。前の画像へ戻るとキャッシュが利用される。
* 読み込み中に別画像を選択、F3で非表示、Workspace切り替え、終了を行い、古い結果が再表示されない。
* Shell Preview Handlerの通常モードと別プロセスモードでサイズ変更を確認する。別プロセスの通知集約はサービス回帰テストでは検証できない。

画像の選択待ちは60ms、リサイズ後の再デコード待ちは160ms。キャッシュは最大64MiB／64件、
デコード後の目標画素数は最大8Mi画素です。コーデック内部の一時メモリ使用量を保証する上限ではありません。
キャッシュの更新判定にはファイルサイズと更新日時を使います。

追加の回帰項目として、Undo途中失敗後の再試行、監視ルートの正規化、ジャンクション循環の拒否、
列挙キャンセル、アイコンの遅延更新通知、重複する復元処理の抑制、保存失敗時の元ファイル保持、
保存要求の順序、大文字・小文字だけのファイル／フォルダのリネームとUndoを確認します。
ジャンクションのテストではWindows標準のPowerShellで検証用リンクを作成してから解除します。
リンク作成が禁止される環境ではテストを失敗として報告します。

今回の修正の実操作確認では、次を確認してください。

* 大量のEXEやショートカットを含むフォルダで、一覧が先に表示され、スクロール後もアイコンが更新される。
* 読み込み速度の異なる複数ペインでWorkspaceを切り替え、選択とスクロール位置が保持される。
* Workspaceを保存してすぐ閉じ、再起動後に保存先・タブ・ペイン構成が復元される。
* ファイルとフォルダをF2で大文字・小文字だけ変更し、Ctrl+Zで元の表記へ戻せる。

成功時は終了コード0、テスト失敗・ビルド失敗・タイムアウト・結果欠落時は1です。
実行ごとに `temp/regression/<一意なID>/` を作り、`results.json`、標準出力／エラーログ、
性能ログ、ビルドログ、検証用ファイルを残します。失敗原因は各チェックの `Error` を確認してください。
起動前の失敗などで結果JSONを生成できない場合は `runner-error.log` を確認します。
成果物は自動削除しないため、不要になった実行フォルダは手動で削除できます。

```powershell
# ビルド済みの同じ構成を繰り返し検証（ソース変更後は通常実行で再ビルド）
pwsh -NoProfile -File ./run_regression_test.ps1 -NoBuild
# 保存先とテスト実行の制限時間を指定（ビルド時間は制限時間に含まない）
pwsh -NoProfile -File ./run_regression_test.ps1 -Configuration Release -TimeoutSeconds 120 -OutputDirectory 'D:\Test Results'
```

通常のFileKakariウィンドウは起動せず、ユーザーの設定・セッションを読み書きしません。
親プロセスの環境変数も変更しません。タイムアウト時に終了するのは、このスクリプトが起動した
テストプロセスとその子だけです。既に起動しているFileKakari、Explorer、Preview Handlerは終了しません。

## Excel / ShellプレビューのDPI・リサイズ確認

自動テスト `preview-host-parent-dpi-and-native-resize` は、非表示のネイティブ親ウィンドウを使い、
親と異なるDPIスレッドからのホスト作成、DPIコンテキストの復元、拡大・縮小、再接続、
GC後のウィンドウコールバックを確認します。Office自体は起動しません。

実操作では、複数シートのExcelファイルをF3でプレビューし、次を確認してください。

* Windowsの表示倍率100%・125%・150%で、シートバーと水平スクロールバーが下端に収まり、表示位置をクリックできる。
* ペインの縦横サイズ変更、F3での再表示、別ファイル選択、Workspace切り替え後もサイズが追従する。
* Excelを初回表示した後、別のExcelや別形式を経由して同じExcelを再表示する操作を繰り返す。約1秒後にシートバーの位置・クリック判定が正常になり、手動リサイズが不要なことを確認する。
* 表示直後の約1秒以内に別ファイル選択・F3で非表示・Workspace切り替えを行い、古いExcelの補正が次のプレビューへ適用されないことを確認する。
* 異なる倍率のモニター間を移動しても、右端・下端の余白やクリック位置のずれが発生しない。
* Word・PDFなど他のShell Preview Handlerでも表示・リサイズが維持される。

診断時は起動前に `FILEKAKARI_PERF_LOG` を書き込み可能なログパスに設定します。
`DPI.Attach` の親・ホストのコンテキスト/DPI、`DPI.Resize` の要求サイズ・実クライアントサイズを比較してください。
このログで追えるのはホスト境界です。Excel内部の子ウィンドウやOfficeのバージョン依存の描画は実操作で確認が必要です。

Excelの非同期レイアウト対策として、読み込み完了通知から約250ms・1000ms後にホストとハンドラーを
1px縮小して即座に戻します（外側のWPFペインのサイズは維持）。`Excel.LayoutRefresh` に適用した要求IDと
実サイズを記録します。この補正は手動リサイズで正常化する症状への対策であり、Office内部の原因を確定するものではありません。

このテストはサービス層の回帰テストです。Shell Preview Handler／PowerToys／WebView2の表示、
PDF・動画・音声の再生、WPF上の選択・スクロール・Workspace復元は別途実操作で確認してください。
旧スクリプトの `FILEKAKARI_AUTO_TEST` は本体に実装がなく、破損したPDF／メディアを置いても
表示の成否を検証できなかったため、合格判定には使用しません。
